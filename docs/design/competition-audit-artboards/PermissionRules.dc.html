Metadata-based content permission rules

Access is decided by what a document is, not by where it sits. Each rule grants or denies a set of operations to a set of roles, for every document whose metadata satisfies its predicate.

1
Enabled is a toggle, not a deletion
A rule is taken out of effect while its intent is preserved for review. The list filters to enabled and disabled separately.
PRM-9PRM-10
2
Grant and Deny are both first-class
Deny exists because some content must be withheld from roles a broader grant would otherwise reach. Which one wins has to be stated in the interface, not only in documentation.
PRM-5PRM-6
3
Operation scope is a set
Read, upload, logical delete — chosen independently. A role that may read and upload but not delete is the ordinary case.
PRM-7PRM-18
4
Roles are read-only, sourced from the identity provider
The rail shows each role with its source. The product consumes roles; it never creates or renames them, and offers no control that would pretend otherwise.
PRM-1PRM-2
5
The predicate is summarised in plain language
department = Executive AND classification = Confidential, readable in the list. A rule whose effect can only be learned by opening it will not be reviewed — and there are 354 of them.
PRM-8PRM-4
6
Deletion of the substrate is guarded
A metadata field referenced by any rule cannot be deleted; the attempt names the rules that block it. Deleting a field out from under a predicate silently changes who can see what.
PRM-14PRM-17

The one thing this screen does not yet show is PRM-12: creating or editing a rule should state how many documents the predicate currently matches, before it is saved. A rule saved blind is a rule nobody can review.
